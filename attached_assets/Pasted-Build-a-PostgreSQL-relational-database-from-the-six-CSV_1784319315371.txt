Build a PostgreSQL relational database from the six CSV files in this project.

The CSV files are:

1. 5e_Bestiary_monsters.csv
2. 5e_Bestiary_monster_traits.csv
3. 5e_Bestiary_monster_actions.csv
4. 5e_Bestiary_action_effects.csv
5. 5e_Bestiary_spellcasting_profiles.csv
6. 5e_Bestiary_monster_spells.csv

These files are not six separate databases. They are six related tables belonging to one database named or described as the 5e Bestiary.

Use PostgreSQL and the DATABASE_URL environment variable supplied by Replit.

Do not flatten the CSV files into one table or store their contents as large JSON documents. Preserve the relational structure described below.

DATABASE RELATIONSHIPS

The monsters table is the central table.

The relationships are:

monsters
├── monster_traits
├── monster_actions
│   └── action_effects
└── spellcasting_profiles
    └── monster_spells

In relational terms:

monsters.monster_id
    → monster_traits.monster_id

monsters.monster_id
    → monster_actions.monster_id

monster_actions.action_id
    → action_effects.action_id

monsters.monster_id
    → spellcasting_profiles.monster_id

spellcasting_profiles.spellcasting_profile_id
    → monster_spells.spellcasting_profile_id

Each arrow represents a one-to-many relationship.

A monster can have many traits, many actions, and multiple spellcasting profiles.

An action can have multiple effects.

A spellcasting profile can have multiple spells.

Import each CSV into the following PostgreSQL table:

PRIMARY KEYS

Use the existing textual IDs supplied by the CSV files as permanent primary keys.

Use:

monsters.monster_id
    TEXT PRIMARY KEY

monster_traits.trait_id
    TEXT PRIMARY KEY

monster_actions.action_id
    TEXT PRIMARY KEY

action_effects.effect_id
    TEXT PRIMARY KEY

spellcasting_profiles.spellcasting_profile_id
    TEXT PRIMARY KEY

monster_spells.monster_spell_id
    TEXT PRIMARY KEY

Do not replace these IDs with auto-incrementing integer IDs.

Do not generate new IDs during import.

An ID such as:

dnd_5e2014_mm_goblin

is already the stable identifier for that monster and must be preserved exactly.

FOREIGN KEYS

Create the following foreign-key constraints:

monster_traits.monster_id
    REFERENCES monsters(monster_id)
    ON UPDATE CASCADE
    ON DELETE CASCADE

monster_actions.monster_id
    REFERENCES monsters(monster_id)
    ON UPDATE CASCADE
    ON DELETE CASCADE

action_effects.action_id
    REFERENCES monster_actions(action_id)
    ON UPDATE CASCADE
    ON DELETE CASCADE

spellcasting_profiles.monster_id
    REFERENCES monsters(monster_id)
    ON UPDATE CASCADE
    ON DELETE CASCADE

monster_spells.spellcasting_profile_id
    REFERENCES spellcasting_profiles(spellcasting_profile_id)
    ON UPDATE CASCADE
    ON DELETE CASCADE

IMPORT ORDER

Because the tables reference one another, import them in this exact order:

1. 5e_Bestiary_monsters.csv
2. 5e_Bestiary_monster_traits.csv
3. 5e_Bestiary_monster_actions.csv
4. 5e_Bestiary_action_effects.csv
5. 5e_Bestiary_spellcasting_profiles.csv
6. 5e_Bestiary_monster_spells.csv

The parent records must exist before their child records are inserted.

For example, a monster must exist in monsters before its traits and actions can be inserted.

An action must exist before its effects can be inserted.

A spellcasting profile must exist before its spells can be inserted.

Create proper database migrations for all six tables.

IMPORT SCRIPT

Create an import script that can be run from the Replit shell.

Use a command similar to:

npm run import:bestiary -- ./data/bestiary

Use the equivalent command if the project is not using Node.js.

The import script must:

1. Locate the six required CSV files.
2. Confirm that every required CSV exists.
3. Read them as UTF-8.
4. Read column names from the CSV headers.
5. Convert empty optional fields to NULL.
6. Trim accidental whitespace around values.
7. Preserve punctuation and internal line breaks.
8. Convert Boolean values safely.
9. Convert numeric values safely.
10. Preserve long text without truncation.
11. Validate all IDs before writing.
12. Detect duplicate primary keys in each file.
13. Detect orphaned foreign keys.
14. Import everything inside one database transaction.
15. Roll back the entire import if validation fails.
16. Import the files in dependency order.
17. Print a detailed completion report.

BOOLEAN NORMALIZATION

Accept the following Boolean formats:

TRUE
FALSE
true
false
1
0

Convert them to PostgreSQL Boolean values.

Do not treat an empty optional Boolean field as false automatically. Preserve it as NULL unless the schema requires a default.

UPSERT BEHAVIOR

Make the import repeatable.

Use an upsert based on the supplied primary key.

When the ID does not exist:

INSERT the record.

When the ID already exists:

UPDATE the existing record using the CSV values.

Running the import a second time must not create duplicate records.

Do not identify records by monster name.

Monster names are not guaranteed to be unique.

Use only the supplied primary keys for upserts.

- Every monster_id is unique.
- Every trait_id is unique.
- Every action_id is unique.
- Every effect_id is unique.
- Every spellcasting_profile_id is unique.
- Every monster_spell_id is unique.
- Every trait monster_id exists in monsters.
- Every action monster_id exists in monsters.
